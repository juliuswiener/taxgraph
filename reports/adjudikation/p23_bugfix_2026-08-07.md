## 3. Fix

Idiom exakt aus den 13 anderen `inst["felder"]`-Stellen in derselben Datei übernommen
(`_kind_kv_pv_summe`, `_kinderbetreuung_summe`): `.get(fid, {}).get("wert")` +
isinstance-Guard vor `int()` (Default `{}`.get("wert") → `None`, `int(None)` würde sonst
genauso knallen):

```python
_preis_v = inst["felder"].get("p23_veraeusserungspreis", {}).get("wert")
_ak_v = inst["felder"].get("p23_anschaffung_herstellungskosten", {}).get("wert")
_wk_v = inst["felder"].get("p23_werbungskosten", {}).get("wert")
preis = int(_preis_v) // 100 if isinstance(_preis_v, (int, float)) and not isinstance(_preis_v, bool) else 0
ak = int(_ak_v) // 100 if isinstance(_ak_v, (int, float)) and not isinstance(_ak_v, bool) else 0
wk = int(_wk_v) // 100 if isinstance(_wk_v, (int, float)) and not isinstance(_wk_v, bool) else 0
```

## 5. Hand-Rechnung § 23 EStG vs. Ring-Ergebnis

**Von Hand:** Veräußerungspreis 200.000€ − AK/HK 150.000€ − WK 5.000€ = **45.000€ Gewinn**.
≥ 1.000€-Freigrenze (§ 23 Abs. 3 S. 5) → voller Betrag steuerpflichtig, nicht nur der
übersteigende Teil. Kein Verlusttopf-Effekt (einzige Instanz, keine Verluste): Verlusttopf
`max(0, 45.000 − 0) = 45.000€` (§ 23 Abs. 3 S. 7). → **einkuenfte_sonstige += 45.000€**.

**Ring (direkter Aufruf, Basisfall: Brutto 60.000€, ledig, sonst neutral):**
```
gesamtbetrag_der_einkuenfte = 103.770 (aus dem trace)
```
103.770€ = 58.770€ (60.000€ Brutto − 1.230€ AN-Werbungskostenpauschbetrag § 9a) + 45.000€
(p23-Gewinn). **Stimmt exakt mit der Handrechnung überein.** Keine Abweichung — kein
Fix-Bedarf über die drei Zeilen hinaus.

Reproduktionsbefehl: eigenständiges Skript (`API.fall_anlegen`/`API.event`/`API.ergebnis`,
`API.FAELLE` auf Tempdir, 4 p23-Felder gesetzt) — `zahl_cent: 3265600`, `trace.kette`
zeigt die o.g. 103.770€ GdE.

## 6. Aufrufer-Prüfung

- **api.py:1023** (`gesamt`-Zweig): `g["einkuenfte_sonstige"] = _p23_ansonsten_einkuenfte(...)`
  — direkte Zuweisung, danach NUR additive `+=` (§22 Nr.3, KiSt-Überhang). Vor dem Fix: Crash.
  Nach dem Fix: korrekter Wert, keine Überschreib-Kollision.
- **api.py:1371** (`rentner`-Zweig): `p23_eink = _p23_ansonsten_einkuenfte(...)`, danach
  `renten += p23_eink` — rein additiv. Gleicher Befund: Crash → korrekter Wert, kein struktureller
  Seiteneffekt.

Beide Call-Sites ändern sich NUR im Sinn „crasht nicht mehr / liefert jetzt eine Zahl" — keine
andere Logik betroffen.

## 7. Warum `tests/test_p23_accessor.py` den Bug nicht fing

Die 12 ursprünglichen Tests (`test_gewinn_seed_*`, `test_freigrenze_seed_*`,
`test_verlusttopf_seed_*`) rufen `R.catala_p23_veraeusserungsgewinn`/`catala_p23_freigrenze`/
`catala_p23_verlusttopf` **direkt** mit von Hand gebauten Plain-Int-Dicts auf
(`{"veraeusserungspreis": 200000, ...}`) — sie gehen NIE über `_p23_ansonsten_einkuenfte`,
`EM.instanzen()`, den Store oder die API-Schicht. Sie testen die reinen Catala-Rechenfunktionen
isoliert, nicht den Accessor-Kleber in `api.py`, der die Werte aus den Store-Instanzen zieht —
genau dort saß der Bug. Der neue Test `test_p23_ueber_ring_accessor` schließt diese Lücke, indem
er den echten `/fall`→`/event`→`/ergebnis`-Pfad durchläuft.
